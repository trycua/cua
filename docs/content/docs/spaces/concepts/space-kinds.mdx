Every Space is one of three kinds. The kind decides how the Space is kept apart
from the machine it runs on, how fast it starts, and which images it runs.

## The three kinds

| Kind | What it is | Runs |
| --- | --- | --- |
| `container` | The image's files in a container on the host's Linux kernel. gVisor (the default where installed) puts its own user-space kernel in between. | Any OCI image |
| `vm` | A full virtual machine with its own kernel and virtual hardware. | A Cua disk image: Linux or Windows (`-disk`), macOS (Lume) |
| `microvm` | The same container image, booted as a small VM with its own kernel. | Any OCI image |

Any OCI image is a full Space on the container and microVM kinds: an image
without cua-spacesd (`alpine:3.20`, `node:20`) gets a static one put in, so
exec, files and ports work. A VM needs a Cua disk image. See
[Choose where sandboxes run](/cua-sdk/guides/local-runtimes#what-differs-locally).

## Isolation, speed and compatibility

| | Container | VM | MicroVM |
| --- | --- | --- | --- |
| Isolation | Shares the host kernel (gVisor filters it) | Its own kernel, hardware virtualization | Its own kernel, hardware virtualization |
| Start | Fastest | Slowest: a whole OS boots | Between: a small kernel boots straight into the image |
| Guest OS | Linux | Linux, Windows, macOS | Linux |
| Checkpoints and forks | Yes | Yes | Yes, except on Apple's Containerization |

Use a container for most Linux work: it starts fastest and runs on the most
machines. Use a VM for Windows or macOS, or a full Linux desktop OS. Use a
microVM to run any Linux image, such as untrusted code, behind its own kernel.

## Which machines run which kind

| Machine | `container` | `vm` | `microvm` |
| --- | --- | --- | --- |
| Mac, Apple silicon | Yes | QEMU; Lume for macOS guests | `vz` on macOS 14 or later; `containerization` on macOS 26 or later |
| Mac, Intel | Yes | QEMU | No |
| Linux with KVM | gVisor or runc | QEMU with KVM | `firecracker` |
| Linux without KVM | gVisor or runc | QEMU under slow emulation | No |
| Windows | Yes | QEMU | No |

The microVM runtimes:

- **`vz`**: Cua's own monitor (`cua-vz`) on Apple's Virtualization framework,
  with checkpoints and forks. It ships next to `cua` in the Mac app and the
  installer. The guest kernel and its network helper download on first use.
- **`containerization`**: Apple's Containerization. Cua downloads Apple's
  `container` (signed by Apple) into `~/.cua` on first use, or run
  `cua runtime setup containerization`. It has no checkpoints or forks. If
  another install of Apple's `container` runs its services, stop them with
  `container system stop`.
- **`firecracker`**: Firecracker on Linux. It needs `/dev/kvm` with read and
  write access. `cua runtime setup firecracker` downloads Firecracker, and the
  guest kernel downloads on first use.

`cua runtime doctor` has a row for each (`firecracker`, `vz`,
`containerization`) that says whether it is ready and what is missing.

An [egress policy](/cua-sdk/guides/egress) is enforced on Firecracker
microVMs. On `vz` and Containerization microVMs it is refused.

### Your own cloud and your other machines

- **Another of your machines** runs the kinds it reports to your account.
- **AWS**: a pool machine needs KVM for VM and microVM Spaces. Of the machine
  types Cua offers, only bare metal (`c6g.metal`) has it. A metal machine costs
  dollars an hour, so a single small request is refused unless you allow it
  with `cua cloud budget --allow-metal on`.
- **Hetzner and Google Cloud**: the machine types Cua offers have no KVM, so
  they run containers only.
- **Modal**: `--on modal --kind microvm` (or `--runtime microvm`) runs the
  sandbox on Modal's VM runtime. Linux images only.

`cua cloud plan --kind microvm` shows where microVM Spaces would go and which
machines the pool would add for them. See
[Use your own cloud](/cua-sdk/guides/your-cloud).

## How the default is chosen

With no kind given, the kind is `auto` and comes from the image:

- macOS and Windows images are VMs.
- An image with a container rootfs is a container.
- An image that only has a disk (a `-disk` containerDisk, a Lume image) is a VM.

`auto` never picks `microvm`. You ask for it.

The runtime is `auto` too: the first one that fits the image and the host.
Containers use gVisor before runc. VMs use QEMU, and Lume for a macOS guest.
MicroVMs use `vz` on a Mac when it is installed, else `containerization`, and
`firecracker` on Linux.

To change your default, set `default.kind` (or `CUA_DEFAULT_KIND` for one shell
or CI job). A default that does not fit an explicit request is skipped. See
[Change the default](/cua-sdk/guides/local-runtimes#change-the-default).

Some tools have their own default: `cua build` builds a VM, and
`cua compat serve` makes VMs where this machine can accelerate them, else
containers.

## Pick a kind

<Tabs groupId="space-kinds" persist items={['CLI', 'Python', 'TypeScript', 'App']}>
  <Tab value="CLI">

```bash test="cli-shape" id="space-kinds-cli"
cua sb create linux --kind microvm --name fast          # runtime auto
cua sb create linux --kind microvm --runtime containerization --name fast2
cua run --kind microvm -- python job.py
cua config set default.kind microvm                     # your default
```

`--kind microvm` works on `cua sandbox create`, `cua spaces create`,
`cua sandbox run`, `cua run`, `cua build`, `cua compat serve`, `cua spaces prewarm`,
`cua sandbox pool create` and `cua cloud plan`. An agent passes `kind: "microvm"`
to the `create_space` or `sandbox_create` tool. `--runtime` picks the engine; a
runtime implies its kind.

  </Tab>
  <Tab value="Python">

```python skip="pseudo"
import cua

spaces = cua.embedded().spaces()
created = await spaces.create(cua.SpaceCreateOptions(kind="microvm"))

# A sandbox, with an explicit runtime:
sb = await cua.embedded().sandboxes().create(
    cua.SandboxCreateOptions(image="linux", kind="microvm", runtime="vz")
)
```

  </Tab>
  <Tab value="TypeScript">

```ts skip="pseudo"
import { embedded, SandboxCreateOptions, SpaceCreateOptions } from '@trycua/cua';

const created = await embedded().spaces().create(
  SpaceCreateOptions.create({ kind: 'microvm' })
);

// A sandbox, with an explicit runtime:
const sb = await embedded().sandboxes().create(
  SandboxCreateOptions.create({ image: 'linux', kind: 'microvm', runtime: 'firecracker' })
);
```

  </Tab>
  <Tab value="App">

In Cua Spaces, press **New Space**, then open **Advanced** in **Choose a
system**. **Kind** offers **Container**, **Virtual machine** and **MicroVM**,
with one line under it that says what the chosen kind is. **Runtime** picks
the engine: for a microVM, the microVM runtimes ready on this machine.

**MicroVM** is offered only when the machine in **Run on** runs microVMs: this
machine when its runtime check has one ready, another of your machines when
it reports the kind. Otherwise it is greyed out, and the line under **Kind**
says why (for example `MicroVM needs macOS 26.` or `MicroVM needs KVM.`). The
app sends the same `kind="microvm"` as the CLI.

  </Tab>
</Tabs>

A kind or runtime the location does not offer fails with `InvalidPlacement`,
and the message lists the valid values.

The [E2B, Daytona and Modal SDKs](/spaces/guides/sandbox-sdks#what-you-get-on-your-own-machines)
take the kind as `cua.kind` in E2B metadata, Daytona labels and Modal
`experimental_options`, and
[cua-e2b](/spaces/guides/sandbox-sdks#use-cua-e2b-in-place-of-e2b) takes
`CUA_E2B_KIND`.
