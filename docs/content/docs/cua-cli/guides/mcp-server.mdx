`cua mcp` is a stdio MCP server with the Spaces tools plus sandbox, computer
and skills tools. `cua daemon mcp` is the same server through `cua daemon`
(started if needed), so several agents share Spaces, streams and sandboxes.
For the machine the agent itself runs on, use
[Cua Driver](/cua-driver/quickstart) instead.

```bash skip="third-party-cli"
claude mcp add cua -- cua daemon mcp
claude mcp add cua -- cua mcp --sandbox dev --permissions sandbox:readonly,computer:all
```

`cua agents setup` adds this entry for detected agents. `--sandbox`
(`CUA_SANDBOX`) is the default target of the computer tools; each call can pass
`sandbox`. Cloud sandboxes use the CLI's
[credentials](/cua-cli/guides/authentication#which-credential-fleet-uses).
Every tool is in [MCP tools](/cua-cli/reference/mcp-tools).

## What the agent sees

The server lists about twenty tools, most with an `action`, to keep the
agent's context small: `list_spaces`, `create_space`, `space` (start, stop,
delete, forget, add), `space_bash`, `space_files`, `computer` and `window`
(a Space's screen), `list_tools` and `call_tool`, `open_browser`, `agent`,
`volume`, `teleport`, `request_site_login`, `share_space`, `show_space`,
`notify_user`, `images`, `approvals` and `more`. `more` lists the rarely used
tools (cloud accounts, persistent agents and routines, hotspot, relay, volume
storage and sync, skills); with a name it describes one, with `arguments` it
calls it.

The per-tool names in the reference (`computer_click`, `stop_space`,
`volume_ls`, ...) still work when called by name, so existing agents and
scripts keep running; they are just not advertised.

## Approvals

Actions that reach beyond the Space the agent works in ask the user for Touch
ID (or the login password) first. Cua Spaces, Settings, Agent approvals lists
them with a switch each, and the server reads the setting on every call.

| Setting | Gated by default | Covers |
|---------|------------------|--------|
| Use the cloud | yes | Cloud Spaces, `cloud_connect`, `cloud_sweep` |
| Add machines | yes | `add_space`, `relay_register_space` |
| Control your machines | yes | Commands, files and input on `relay:` and `direct:` Spaces, creating on `host:` |
| Send sensitive files | yes | Uploading SSH keys, cloud credentials, browser profiles, the Cua home |
| Share API keys | yes | `env_from_host` on agent runs |
| Run on a schedule | yes | Routines |
| Change Volume storage | yes | `volume_storage_set`, mount, unmount |
| Share your network | yes | `hotspot_start` |
| Show things on your screen | no | Viewer, picture in picture |

Teleport, site logins, sharing a Space, volume grants and computer access
always ask. Agents cannot approve requests or change access: `volume_approve`,
`volume_grant` and the other grant tools are refused (`forbidden`), and the
settings file is changed only with the user's fingerprint. Downloads into the
Cua home, `~/.ssh`, `~/Library/LaunchAgents` and similar folders are refused.
The Volume tools run as the calling agent (`host-<client>`), not as the user.

A refused call returns `approval_denied`; the agent should stop and tell the
user. `cua mcp --approvals never` refuses every gated action without asking
(for servers with no screen). A build without Cua Spaces cannot ask, so it
refuses them too.

Start a new Hermes session (or run `/reload-mcp`) to load the server.

## Permissions

`--permissions` (`CUA_MCP_PERMISSIONS`) takes `group:action` strings and groups,
comma-separated. Only granted tools are listed; others are refused.

| Group | Expands to |
|-------|-----------|
| `all` | Everything. |
| `spaces:all`, `spaces:readonly` | Every Spaces tool, or the read-only ones (`list_spaces`, `download`, `agent_status`, ...). |
| `sandbox:all` | `sandbox:list`, `create`, `delete`, `start`, `stop`, `restart`, `suspend`, `get`, `view` |
| `sandbox:readonly` | `sandbox:list`, `sandbox:get` |
| `computer:all` | `computer:screenshot`, `click`, `type`, `key`, `scroll`, `drag`, `hotkey`, `clipboard`, `file`, `shell`, `window`, `accessibility` |
| `computer:readonly` | `computer:screenshot` |
| `skills:all`, `skills:readonly` | `skills:list`, `read`, `record`, `delete`, or only `list` and `read` |

<Callout type="warn">
  Only an empty list grants everything. An unknown permission is skipped with a
  warning; if nothing valid remains no tools are registered, so a typo fails
  closed.
</Callout>

## Choose a grant

`computer:shell`, `computer:file`, `spaces:space_bash` and `spaces:teleport_app`
run commands, touch files or use your app sessions in the target;
`sandbox:delete` and `spaces:delete_space` destroy sandboxes.

| Intent | Grant |
|--------|-------|
| Look, not touch | `sandbox:readonly,computer:readonly,spaces:readonly` |
| Drive a UI without a shell | `computer:screenshot,computer:click,computer:type,computer:key,computer:scroll` |
| Automate one sandbox | `computer:all` with `--sandbox <name>` |
| Spaces agent | `spaces:all` |

Computer-tool coordinates are in the pixel space of the last
`computer_screenshot` (capped at 1200 px on the long edge). Spaces tools that
need cua-spacesd return `capability_missing` on images without it; see
[Use Spaces from an agent](/spaces/guides/use-from-an-agent).
