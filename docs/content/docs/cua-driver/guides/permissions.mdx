Every call, from the CLI, MCP, the SDK, or a daemon, passes the same
authorization check inside the runtime before it touches the desktop. The
trusted launcher configures it at startup; an agent cannot change it from a
tool call, and a running daemon cannot be reconfigured (restart it).

Every call must pass all of these layers, and each can only narrow:

1. Hard invariants, such as self-targeting and protected-host checks.
2. The built-in tool and risk map.
3. Administrator policy, `CUA_DRIVER_MANAGED_POLICY_FILE`.
4. User policy, `CUA_DRIVER_POLICY_FILE`.
5. The permission mode.
6. The capability manifest, when configured.
7. A launch grant or host decision for a residual boundary.

## Choose a mode

| Mode | Use it for | Behavior |
| --- | --- | --- |
| `standard` (default) | Local CLI and MCP use | Observation, input, isolated browsers, recording, and validated file transfer run without prompts. Attaching to a logged-in browser profile still needs a grant. |
| `bounded` | Unattended agents, gateways, embedded apps | A capability manifest is required. In-scope work is silent; everything else is denied. |
| `unrestricted` | Disposable or fully trusted machines | Cua approval checks are bypassed. No protection against prompt injection. |

```bash test="cli-shape" id="cua-driver-serve-bounded"
cua-driver serve \
  --permission-mode bounded \
  --capability-manifest ~/cua-session.yaml \
  --approve-capability-manifest
```

```bash test="cli-shape" id="cua-driver-serve-unrestricted"
cua-driver serve --dangerously-bypass-approvals
```

`--permission-mode unrestricted` alone fails closed. Add the two manifest flags
to `standard` or `unrestricted` to narrow them too. On macOS, pass the flags
after `serve` when you start the installed app by its exact path
(`open -n -g /Applications/CuaDriver.app --args serve …`), and use an absolute
manifest path.

What `standard` allows:

| Operation | Standard |
| --- | --- |
| Observe windows, apps, and the desktop; click, type, scroll, drag | Allow |
| Driver-owned isolated browser; read page content | Allow |
| Upload, download, screenshot, record to validated paths | Allow |
| Terminate a process this runtime launched | Allow (fingerprint rechecked) |
| Attach to a logged-in Chromium profile | Needs `--grant existing-profile` or host approval |
| Terminate a foreign process; raise an OS permission prompt from a tool; legacy page mutations; unknown risky operations | Deny |

Input that would land on a macOS security or consent prompt (an administrator
password sheet, a privacy "would like to access" alert, an Accessibility or
Gatekeeper warning) is refused with `security_prompt_protected` in `standard`
and `bounded` mode; answering it is the user's call. Reading the prompt stays
allowed. Only `unrestricted` mode lets input reach it, for disposable machines
such as a VM being prepared unattended.

### Without CLI flags

`cua-driver mcp` on Windows and Linux, the Windows autostart task, and
embedding hosts read the same settings from the environment:

| Flag | Environment variable |
| --- | --- |
| `--permission-mode <mode>` | `CUA_DRIVER_PERMISSION_MODE=<mode>` |
| `--capability-manifest <path>` | `CUA_DRIVER_CAPABILITY_MANIFEST_FILE=<path>` |
| `--approve-capability-manifest` | `CUA_DRIVER_CAPABILITY_MANIFEST_APPROVED=1` |
| `--dangerously-bypass-approvals` | `CUA_DRIVER_DANGEROUSLY_BYPASS_APPROVALS=1` |

`unrestricted` needs both the mode and the bypass variable; `bounded` needs the
manifest and its approval. A missing half fails startup instead of falling back
to `standard`. Anyone who can set these variables sets the mode: protect them
like the unit file or task that carries them. To keep a mode across reboots,
see [Pin a permission mode](/cua-driver/guides/operate#pin-a-permission-mode).

## Write a capability manifest

A manifest is deny by default: a tool must be in `allow.tools` and every
resource it touches must match. It narrows any mode and never widens one.

```yaml test="config" id="yaml-config-manifest"
version: 3
expires_after: 8h
idle_timeout: 30m

allow:
  tools:
    - start_session
    - end_session
    - launch_app
    - get_window_state
    - click
    - type_text
    - press_key
    - kill_app

resources:
  apps:
    - executable: /usr/bin/example-editor   # macOS: bundle_id: com.example.Editor
      launch: true
      windows: all
      terminate: driver_launched

  files:
    read:
      - dir: /data/input
        recursive: true
    write:
      - dir: /data/output
        recursive: true

  desktop:
    display: false
```

- Apps: `bundle_id` on macOS, an absolute `executable` on Windows and Linux.
  `terminate: driver_launched` only kills a process this runtime started.
  `launch_app` needs `launch: true` on a matching entry, and the call must name
  the app by that exact `bundle_id` or absolute path, not by display name.
- Files: roots are compared by canonical path component; `recursive: false`
  allows direct children only.
- `desktop.display: true` allows full-display capture and screen-coordinate
  input. Keep it `false` unless needed.
- `expires_after` and `idle_timeout` are optional, but required in `bounded`.
- Version 1 and 2 manifests still load; their `ask.tools` entries are denied.

<Callout type="warn">
  A manifest that lists `resources.browser.origins` may only use the typed `browser_*` tools.
  Generic input and observation (`click`, `type_text`, `get_window_state`, `get_desktop_state`,
  `page`, and similar) see whatever tab is open, so the runtime refuses to start with both. Run
  browser work and desktop work in two runtimes, and scope the desktop one away from the browser
  with `desktop.display: false`. A standard runtime without a manifest can type into any window,
  which defeats another runtime's origin list.
</Callout>

A browser-only manifest:

```yaml test="config" id="yaml-config-browser"
version: 3
expires_after: 8h
idle_timeout: 30m

allow:
  tools:
    - start_session
    - end_session
    - launch_app
    - list_windows
    - browser_prepare
    - get_browser_state
    - browser_navigate
    - browser_click
    - browser_type
    - browser_download

resources:
  browser:
    profiles:
      - kind: isolated        # or existing_profile for a logged-in profile
    origins:
      - https://app.example.com

  desktop:
    display: false
```

Test it before unattended use: an allowed call succeeds silently, the same tool
against another app, origin, or path returns
`bounded_resource_outside_manifest`, and an unlisted tool returns
`permission_denied`. To point an MCP client at the bounded daemon:

```json test="config" id="json-config" schema="mcp-client-config"
{
  "mcpServers": {
    "cua": {
      "command": "cua-driver",
      "args": ["mcp", "--socket", "/path/to/cua-driver.sock"]
    }
  }
}
```

## Revoke

```bash test="cli-shape" id="cua-driver-revoke"
cua-driver revoke --session research-1
cua-driver revoke --all
```

Ending a session removes its grants, browser bindings, recordings, and cursor;
its label stays retired until `start_session` declares it again. `revoke --all`
suspends the whole runtime (calls return `authorization_suspended`) until you
restart it.

## Restrict tools with a policy

A policy file limits which tools an agent may call and with which arguments.
It is deny by default once set, loaded once at startup, and a missing or
invalid file stops the daemon from starting.

```yaml test="config" id="yaml-config-policy"
allow:
  tools:                       # allowed with any arguments
    - screenshot
    - get_window_state
    - list_apps
    - list_windows
    - press_key
    - wait
  rules:                       # allowed when every constraint passes
    - tool: click
      constraints:
        delivery_mode:         # absent means the tool default
          optional: true
          allowed: [background]
        scope:                 # desktop clicks always use foreground input
          optional: true
          allowed: [window]
    - tool: type_text
      constraints:
        text:
          max_length: 500
          pattern: "^[\\x20-\\x7E\\n\\t]*$"
    - tool: scroll
      constraints:
        amount:
          min: -20
          max: 20
    - tool: launch_app
      constraints:
        bundle_id:
          allowed: ["com.apple.Safari", "com.google.Chrome"]
deny:
  tools:                       # checked first
    - shell_execute
```

Evaluation: `deny.tools` → `allow.tools` → any matching `allow.rules` entry →
deny. Constraint checks are `min`, `max`, `max_length`, `pattern` (RE2 syntax),
`allowed`, and `items`, which applies its own checks to every element of an
array argument. A constrained argument must be present unless the constraint
sets `optional: true`; an absent optional argument passes and the tool uses
its default. The run_script helpers, which omit `delivery_mode`, therefore
pass `delivery_mode: { optional: true, allowed: [background] }`. Check what
the default does before relying on it: a `scope: desktop` click with no
`delivery_mode` uses foreground input, which is why the example also limits
`scope`. A rule passes whatever other arguments the call carries, so forbid
any argument that overrides a constrained one with `optional: true` and
`allowed: []`. `allow` and `deny` also accept a flat list of names.
`type_text_chars` is normalized to `type_text`.

The `bundle_id` rule above is for macOS. On Windows, `launch_app` prefers
`launch_path`, then `path`, over `bundle_id`, so a Windows policy pins `path`
and forbids the arguments that would override it:

```yaml test="config" id="yaml-config-policy-windows-launch"
allow:
  rules:
    - tool: launch_app
      constraints:
        path: { pattern: '^C:\\Windows\\System32\\notepad\.exe$' }
        launch_path: { optional: true, allowed: [] }   # must be absent
        urls: { optional: true, allowed: [] }
        additional_arguments:
          optional: true
          items: { pattern: '^[\w.-]+\.txt$' }
```

### Limit actions to one app

`constraints` check the arguments the caller sent. A `pid` or `window_id`
there is a number the caller chose, so it cannot prove which app an action
reaches. A rule's `target` block checks what the driver attested instead: it
reads the window's owner and that process's executable from the operating
system, and evaluates the rule on that.

```yaml test="config" id="yaml-config-policy-target"
allow:
  rules:
    - tool: click
      target:                  # driver-attested, never caller input
        executable:
          allowed: [/System/Applications/TextEdit.app/Contents/MacOS/TextEdit]
    - tool: type_text
      target:
        kind: { allowed: [window] }   # not desktop-wide typing
        executable:
          allowed: [/System/Applications/TextEdit.app/Contents/MacOS/TextEdit]
```

The attested target has these fields. A field the platform cannot attest is
absent, and a constraint on an absent field fails unless it sets
`optional: true`.

| Field | Value |
|---|---|
| `kind` | `window` (the call names a `pid` and its `window_id`, or an `element_token` from a window's snapshot) or `desktop` (neither; process fields are absent) |
| `pid`, `window_id` | The window's owner as the OS verifies it, and the window. On X11 the owner comes from the X server's X-Resource extension, never the `_NET_WM_PID` a client sets; a window whose owner the server cannot report (a remote client, no XRes 1.2) has no attested target. Wayland sessions cannot verify window owners yet, so only desktop targets attest there |
| `executable`, `process_start_time` | The process instance, read from the OS for that pid. On Windows a packaged app's window belongs to `ApplicationFrameHost.exe`; the driver reports the hosted app's process instead |

App names and bundle ids are not attested fields. `list_apps` matches running
processes to installed apps by executable or command-line name on Linux and
Windows, so its names identify what to launch, not which process a window
belongs to. Use `executable`, with `pattern` for a path that varies.

`target` applies to `click`, `double_click`, `right_click`, `drag`, `scroll`,
`move_cursor`, `mouse_button_down`, `mouse_button_up`, `mouse_drag`,
`type_text`, `press_key`, `hotkey`, `set_value`, `bring_to_front`,
`set_window_frame`, `get_window_state`, `get_accessibility_tree`,
`get_desktop_state`, and `zoom`. An unknown field, or `target` on any other
tool, stops the daemon from starting.

Before it checks the policy, the driver refuses with
`target_identity_unavailable` when the named window is closed or belongs to
another pid, an `element_token` names no live snapshot window, or the process
cannot be identified. It also refuses selectors that could name different
targets, because platforms resolve them differently: a `window_id` without its
`pid`, a `pid` without its `window_id` (the platform would pick which of the
process's windows receives the action), an `element_token` whose window
disagrees with the declared `pid` or `window_id`, or an `element_token` with
`scope: desktop` and no `pid`.
`mouse_drag` and `mouse_button_up` deliver to the window `mouse_button_down`
holds, so under a `target` rule they must name that window's `pid` and
`window_id`; the tool refuses ones that do not match the hold. As the last step before the platform tool runs, after
consent, input-lane admission, and any recording capture, it attests the
target again and refuses with `target_identity_changed` if anything differs, for example a pid reused by a
new process. A window or process that disappeared by then refuses with
`target_identity_unavailable`. The OS can still change focus or close a window
between that last check and input delivery; the check narrows that window,
it cannot close it. An `allow.tools` entry for the same tool allows every
target.

```bash test="cli-shape" id="cua-driver-serve"
CUA_DRIVER_POLICY_FILE=~/.cua-driver/policy.yaml cua-driver serve
```

```bash test="cli-shape" id="cua-driver-call"
cua-driver call shell_execute '{"command":"echo hello"}'
# Error: tool 'shell_execute' is explicitly denied
```

For programmable rules, point the variable at a `.rego` file, or a directory
of `.rego` files loaded in filename order. The rule `data.cua.policy.allow`
must be a boolean; `undefined` denies. The input is
`{"server": "cua-driver", "tool": "<name>", "arguments": {…}, "target": {…}}`,
where `arguments` is what the caller sent and `target` is the driver-attested
target described above, or `null` for a tool without one. With a Rego policy
the driver attests the target of every call to those tools.

```rego skip="pseudo"
package cua.policy

import rego.v1

safe_tools := {"get_window_state", "list_apps", "list_windows", "click", "press_key", "wait"}

allow if {
    input.tool in safe_tools
}

allow if {
    input.tool == "type_text"
    count(input.arguments.text) <= 500
    input.target.kind == "window"
    input.target.executable == "/System/Applications/TextEdit.app/Contents/MacOS/TextEdit"
}
```

A managed policy (`CUA_DRIVER_MANAGED_POLICY_FILE`) uses the same formats; a
call must pass both. `cua-driver status` shows a hash of each loaded policy.
Policies decide which calls run. They do not filter responses, rate-limit, or
authenticate callers, and code running inside the runtime's process can bypass
them. A browser `browser_navigate` host allowlist also cannot stop a page from
redirecting after a click.

## Host authorization

An embedding app can install a `DriverAuthorizationHost` callback to decide
residual `standard` boundaries itself, and a `DriverActivityObserver` for
content-free events (see [Use the SDK](/cua-driver/guides/use-the-sdk#constructors)).
Without a grant or callback, a residual boundary returns
`authorization_required`; Cua never shows its own modal. Same-user code and
malware on the same desktop are outside this boundary.
