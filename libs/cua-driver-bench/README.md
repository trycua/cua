# Cua Driver Bench

Cua Driver Bench measures how well a computer-use tool layer lets an agent get
real desktop work done, and whether it can do that work in the background
without taking the user's focus, keyboard or pointer. Within each agent
harness, the agent, the model, the prompts and the limits are the same for every
setup; only the computer-use tool changes.

This directory holds the harness, the public task set and the method of
**Bench v2**. The ten Bench v2 tasks run on macOS, Linux and Windows. The
measurement on macOS assumes a macOS 26 desktop.

### Reading and rerunning the release results

* **What is scored.** Success and the background headline follow
  [`METHOD.md`](METHOD.md): *full pass* is the checker passing with no GUI-only
  violation and, in the background condition, all eight user-undisturbed
  criteria held. The background headline covers the eight tasks that run in the
  background; MB-10 and MB-11 (foreground only) are scored in the foreground
  condition only.
* **Versions.** Each table names the driver versions it used: the same on
  both macOS conditions, different on Windows (see "Driver versions are named
  per platform" in `METHOD.md`). Rerun with the version you want
  to measure and record it.
* **Rerun on your platform.** macOS: steps 1 to 5 under "Reproduce", one
  condition per run. Linux: "Linux (the BenchLab tasks)". Windows: "Windows". Then `tools/analyze_v2.py` on the run directories. The
  manifest decides which tasks run in which condition, so a rerun needs no task
  list.

## Fairness and health checks

A trial is scored only when the harness gave the agent a working environment.
[`fairness/SPEC.md`](fairness/SPEC.md) defines the checks and
[`fairness/cdb_fairness.py`](fairness/cdb_fairness.py) implements them with the
standard library only, as functions and a command line, so any runner can use
them:

* **Tool-server preflight.** The setup's MCP server must start, answer
  `initialize` and list its tools (optionally pass one probe call) before the
  agent starts, and the agent session must report it connected.
* **Per-reset health.** After each reset: every app the task's reset or export
  automates accepts Apple events (Automation consent present), loopback works and
  the task's local web app is ready, and every program the checker needs
  (`python3`, `node` for CDB-G04, `osascript`, `xattr`) is on the checker's PATH.
* **Environment watchdog.** During the agent phase the runner probes the
  environment; if it is lost, the trial is a harness error.
* **Harness error, re-run, never scored.** A trial that fails any of these, or
  whose export step or evaluator produces no result, is re-run with the same seed
  and never counted as a pass or a fail. A trial that only ever has harness
  errors is reported as excluded.
* **Seeds per trial index.** `seed = int(sha256(f"{task}:{run_index}")[:8], 16) mod 10^6`,
  with `run_index` counting from 0 per task, the same for every setup and for a
  re-run.

The runner here calls the per-reset checks before every pack-task trial.

## Method in brief

The full method, with the reasons for each rule, is in [`METHOD.md`](METHOD.md).

* **Pre-registration.** The protocol was committed before the first trial, and
  every change since is a dated amendment committed before the trials it covers.
  `METHOD.md` lists the commits.
* **One agent per harness, different tools.** The Claude Code setups run
  `claude -p` with Claude Sonnet 5.5; the Codex CLI setups (Amendment 23) run
  `codex app-server` with GPT-6.1 Sol (`gpt-6.1-sol`, default effort low). Within a harness every
  setup gets the same system prompt, the same built-in tools and the same
  limits: 360 s and 45 turns per trial.
* **Two conditions.** In the *foreground* condition a small witness window is
  in front at the start and the agent may take focus. In the *background*
  condition a "User activity" window stays in front and types one character a
  second, as a user would; the target app is behind it, partly covered, and the
  brief asks the agent to leave that window in front and in focus.
* **GUI-only guard.** Agents get no shell or file tools. A live guard ends a
  trial, and fails it, if the agent reaches a shell through the GUI (Terminal,
  Script Editor, Automator, Shortcuts) or sends code that runs outside the GUI
  through a computer-use tool.
* **Checkers, not judges.** Each task's checker reads the app's final state and
  event log. No model grades anything.
* **Runs.** 5 runs per task, setup and condition (3 in phase 1, then 2),
  interleaved across setups, with a seed per task and run that every setup
  shares.

## Metrics

| Metric | Definition |
| --- | --- |
| Success | The checker passed every required check. A GUI-only violation is a fail. |
| Background completion | Background condition only, the primary metric. From the next full run it follows the multi-player rule of Amendment 22: the trial passed **and** the user could have kept working undisturbed, as if two people shared the computer. None of eight disturbances may happen: loss of key focus, a window raised over the user window, the user's typing lost or redirected (or any keystroke, click or scroll landing in the user window), the real pointer moving more than 1 px, a clipboard change, a Space or full-screen switch, a sheet or dialog on the user's app, or the user's app being deactivated or activated. A criterion that was not measured counts as a disturbance. Each criterion is also reported as its own column. The earlier definition (Amendment 15: focus, key status, raises, typing; pointer not counted) is still reported next to it. |
| Focus steals | Times the frontmost app changed away from the witness or user window |
| Key loss | Times the witness or user window lost key status |
| Windows raised | Times a window of another app appeared above the witness or user window. Windows owned by the computer-use tool itself (an agent cursor, a status banner) are logged but not counted. |
| User keystrokes swallowed | Simulated user keystrokes that never reached the user window, because it was not active and key |
| Pointer moved | The real pointer moved. Part of background completion from Amendment 22 (more than 1 px); under the earlier definition it was recorded (more than 10 px) but not counted. |
| Interruption handled | IR tasks: the interruption was shown, appeared before the final action, and was answered safely |
| Cost, turns, wall time | Claude Code's equivalent cost, model turns and agent wall time per trial |

Success and background completion are reported as k/n with a Wilson 95%
interval, overall and per category. With n = 5 per task and setup, per-task and
per-category differences are directional only.

## Reproduce

You need an Apple silicon Mac that is not your daily machine, or better, a
macOS VM on one. The registered runs used one [Lume](../lume) macOS VM.

### 1. Prepare the macOS VM

| Item | Registered runs |
| --- | --- |
| macOS | 26.5.2 (25F84), Apple silicon |
| VM | 6 CPU, 12 GB, display 1920 x 1080 (System Settings > Displays, not the scaled 960 x 540 mode). The task windows assume this size. |
| Claude Code | 2.1.289 at `/opt/homebrew/bin/claude` (`npm i -g --prefix /opt/homebrew @anthropic-ai/claude-code@2.1.289`) |
| Python | 3.12 at `/opt/homebrew/bin/python3` |
| Tools | ffmpeg (screen recordings), Node 22 or later, Google Chrome, LibreOffice and GnuCash (CDB-G02 to CDB-G04), Xcode Command Line Tools (`xcrun swiftc`) |
| Login | `CLAUDE_CODE_OAUTH_TOKEN` from `claude setup-token`, in a 0600 file named by `CDB_CLAUDE_TOKEN_FILE`; the runner passes it to `claude` by file descriptor |

Keep the desktop clear: windows that cover BenchLab break real-input clicks.

### 2. Get the harness and build the apps

```bash
export CDB_BENCH_WORK=~/bench-work
mkdir -p "$CDB_BENCH_WORK/src"
cp -R libs/cua-driver-bench/automated-eval/macos_bench "$CDB_BENCH_WORK/src/"
cp -R libs/cua-driver-bench/taskpack "$CDB_BENCH_WORK/taskpack"
cd "$CDB_BENCH_WORK/src/macos_bench"
swift/build.sh "$CDB_BENCH_WORK/build"     # BenchLab.app and BenchSentinel.app, ad-hoc signed
```

Install the task apps' Electron dependency, pinned by each lockfile. npm 12 may
skip Electron's postinstall; run its installer in each app if `dist` is missing:

```bash
for app in "$CDB_BENCH_WORK"/taskpack/tasks/shared/*/apps/*; do
  (cd "$app" && npm ci &&
    { [ -d node_modules/electron/dist ] || node node_modules/electron/install.js; })
done
```

### 3. Install each setup

* **Cua Driver.** Build Cua Driver from the pinned main commit inside the VM
  with the scripts in [`tools/vm_main_build/`](automated-eval/macos_bench/tools/vm_main_build)
  (`build_main.sh`, `assemble_main.sh`, `assemble_script.sh`, then
  `tcc_grant.sh` for each app; they need SIP off in the VM). Record the binary,
  skill and script hashes in `pins.json` `cua_main`. The baseline release is
  installed with `python3 tools/install_cua_driver.py`, which checks the
  release assets against `pins.json` and never touches an installed driver.
  Grant the private apps Accessibility and Screen Recording.
* **Codex Computer-Use (Sky).** Install the ChatGPT app at the version in
  `pins.json` and copy `~/.codex/computer-use/Codex Computer Use.app` and the
  `unified-computer-use` plugin cache into the VM. Do not launch the ChatGPT app
  in the VM: it updates itself and rewrites the plugin cache. Give "ChatGPT
  Computer Use" Accessibility and Screen Recording. The launcher writes the MCP
  config from the plugin's own file (`tools/make_codex_cu_mcp.py`). The plugin
  is OpenAI's and is not redistributed here; driving it from a client other
  than OpenAI's is undocumented.
* **Claude Computer-Use (Desktop helper)** (arm `cc-claude-cu-helper`). In the
  VM only, run `zsh tools/claude_cu_helper/install_cu_helper.sh`. It downloads
  Claude Desktop 2.31226.0 from Anthropic's own URL, checks the archive size and
  sha256 and the helper's sha256 and signature against `pins.json`
  (`claude_cu_helper`), unpacks it without moving it to `/Applications` or
  launching it, and builds `winlist` and `cu-disclaim` from source. Then give
  `app-cu-helper` Accessibility in System Settings. Separately grant Apple's
  `/usr/sbin/screencapture` Screen Recording: System Settings → Privacy & Security
  → Screen Recording → **+**, then Go to `/usr/sbin/screencapture`.
  The launcher wraps both helper and capture; Terminal, the adapter and launcher
  receive no new grants. No Claude Desktop binary,
  app code or asset is included in this repository; only Cua's adapter is.
* **Vercel agent-desktop** (arm `cc-agent-desktop`). In the VM, `npm install --prefix "$CDB_BENCH_WORK/agent-desktop" agent-desktop@1.2.0 --allow-scripts=agent-desktop` (npm 11; the package carries the prebuilt binaries and the install script only links the one for your platform). Give the `agent-desktop` binary Accessibility and Screen Recording in System Settings. Check it with `"$CDB_BENCH_WORK/agent-desktop/node_modules/.bin/agent-desktop" --version`. To use a binary elsewhere, set `CDB_AGENT_DESKTOP_BIN`. The adapter is `tools/agent_desktop/ad_mcp.py`; its `ad-instructions.md` is the skill text from the agent-desktop package (Apache-2.0, Vercel Labs), unmodified. The adapter offers the observe, act, window, clipboard and wait commands, and leaves out the skills, session, trace, notification, permission and system-surface commands. Physical input (`headed`) is the model's choice on the tools that can move the pointer, and forced on the tools that only exist as pointer input (`hover`, `drag`, `mouse_*`).
* **Browser Use macOS harness** (arm `cc-browser-use`). In the VM, `python3 -m venv "$CDB_BENCH_WORK/browser-use-harness/venv" && "$CDB_BENCH_WORK/browser-use-harness/venv/bin/pip" install macos-harness==0.2.1`, then run `macos-harness doctor` once by hand and approve what it asks for (Accessibility and Screen Recording for the helper it starts); the adapter refuses `doctor`, `install` and `approve` so the model cannot change the setup. Set `CDB_MACOS_HARNESS_BIN` to use another install. The adapter `tools/browser_use_harness/bu_mcp.py` reads the skill from `macos-harness skill`, so the instructions always match the installed version. `BU_SHOT=always` attaches the screenshot to every `get_app_state`; the default is the vendor's: only when the model opens the file named on the `Screenshot` line.
* **Codex Computer-Use (Sky): what you need before it works.** This arm drives OpenAI's computer-use plugin from the ChatGPT desktop app. It needs the ChatGPT desktop app with **Computer Use enabled** (Settings → Computer use → Any App) and you must sign in with **your own ChatGPT account that has Work or Codex access** (the app sign-in, or `codex login --device-auth` for the bundled Codex CLI). No credentials are shipped here or read by the harness. It is OpenAI's plugin with Claude choosing the actions through an MCP bridge, not OpenAI's own agent: the numbers describe the plugin as a tool layer under Claude Sonnet 5.5, not what OpenAI's agent can do with it. It is not available on Linux yet ([compatibility and limitations](https://learn.chatgpt.com/docs/linux/linux-app#compatibility-and-limitations)), and on Windows it runs foreground only ([Computer Use](https://learn.chatgpt.com/docs/computer-use)). The macOS release run used ChatGPT app 26.930; the Windows run used the ChatGPT/Codex app 26.1029.9216.0.
* **Codex CLI setups** (arms `cx-codex-cu`, `cx-cua-driver`, `cx-claude-cu-helper`). Nothing extra to install beyond the matching Claude Code setup: they use the Codex CLI bundled in the same ChatGPT app (`Contents/Resources/codex-cli/CodexCLI.app`) and the MCP config of the matching Claude Code setup (`cc-codex-cu`, `cc-cua-driver-script` or `cc-claude-cu-helper`). Point `CDB_CODEX_GATEWAY` at an OpenAI-compatible Responses endpoint serving `gpt-6.1-sol` (default `http://127.0.0.1:4000/v1`). The pinned CLI build is in `pins.json` (`codex_native`).

**Terms checks (open).** Two questions have not been reviewed:

* **OpenAI:** driving Codex Computer-Use from a client other than OpenAI's
  (the Claude Code setup) is undocumented, as noted above.
* **Anthropic:** nobody has reviewed Anthropic's terms on driving Claude
  Desktop's computer-use helper from a third-party adapter, or on publishing
  its results. The helper is an internal interface, not an Anthropic-supported
  procedure.

### 4. Check, then run

```bash
cd "$CDB_BENCH_WORK/src/macos_bench"
export CDB_BENCH_DISPOSABLE=1      # the runner may kill Electron, Chrome, LibreOffice and GnuCash by name
python3 run_bench.py preflight --offline --bench-v2 --build-dir "$CDB_BENCH_WORK/build"
python3 run_bench.py preflight --bench-v2 --build-dir "$CDB_BENCH_WORK/build" \
  --arms cc-cua-driver-script cc-codex-cu
```

The preflight checks every pin (driver binary and skill hashes, Claude Code,
macOS and Codex versions, and the tree digest of each pack task), starts each
MCP server and makes three small Haiku calls. Then start a run from a
Terminal.app shell, one condition at a time:

```bash
python3 run_bench.py run --bench-v2 --condition background --park-pointer \
  --arms cc-cua-driver-script cc-codex-cu \
  --phase1-runs 3 --phase2-runs 2 --run-id v2-background --build-dir "$CDB_BENCH_WORK/build"
python3 run_bench.py run --bench-v2 --condition foreground --park-pointer \
  --arms cc-cua-driver-script cc-codex-cu \
  --phase1-runs 3 --phase2-runs 2 --run-id v2-foreground --build-dir "$CDB_BENCH_WORK/build"
```

`launch/launch_bench.command` wraps the same command with the quota gate and a
log, and `launch/watch_bench.py` shows live status. A run resumes when started
again with the same `--run-id`. See [`RUNNER.md`](automated-eval/macos_bench/RUNNER.md)
for the gates, retries and stop rules.

**Evaluator isolation (optional).** By default the task evaluators run as the
bench user. The registered runs ran them as a separate OS user that the agent's
user cannot read (`CDB_EVAL_SUDO=1`, through `/usr/local/libexec/cdb-eval-run`;
see `cdb_adapter.py` for the call). Every tool input is also scanned for
evaluator and oracle paths, and the row records any peek.

### 5. Analyse

```bash
python3 tools/analyze_v2.py "$CDB_BENCH_WORK/runs/v2-background" "$CDB_BENCH_WORK/runs/v2-foreground" \
  --md report.md --json report.json
```

The report gives, per setup, overall and per category: success and background
completion with Wilson intervals, focus steals, key loss, windows raised,
swallowed keystrokes, GUI-only violations with evidence, and the interruption
rates. Keep raw results, streams and recordings out of git.

`run_bench.py --arms cc-agent-desktop` inside the session; or all ten tasks through the XFCE launcher below). The Browser Use harnesses exist for macOS and Windows only, and
Codex computer use is not available on Linux yet
([compatibility and limitations](https://learn.chatgpt.com/docs/linux/linux-app#compatibility-and-limitations)).
`tests/test_linux_session.py` and `tests/test_linux_tools.py` check the session and the tools without a model.

### Linux XFCE (all ten tasks)

[`launch/xfce_session.py`](automated-eval/macos_bench/launch/xfce_session.py) runs one trial of any of the ten Bench
v2 tasks on an X11 desktop with an EWMH window manager (XFCE 4.18 with xfwm4 here), as the desktop user. The BenchLab
tasks use `linux/benchlab.py` and `linux/sentinel.py`; the three multi-app tasks (CDB-G02 to CDB-G04) reset their
workspace and start their apps from the task's own `platform/launch.linux.json`. It parks the pointer, arms the
sentinel, runs your agent command under the GUI-only guard, stops it at the limit, runs the checker and writes
`row.json` next to the transcript, the sentinel log, the app logs and the final workspace. The Linux XFCE rows of
the Bench v2 report (agent-desktop 1.2.0 and a cua-driver 0.38.0 cross-check, 5 trials per task, 6 Nov 2026) were run
with exactly this.

**1. The desktop.** Ubuntu 24.04 with XFCE 4.18 on Xvfb at 1920 x 1080, as an image or a VM:

```sh
# Cua's Linux image (XFCE on Xvfb); CUA_RESOLUTION sets the 1920x1080 the shared window frames need
docker run -d --name bench-xfce -e CUA_RESOLUTION=1920x1080 ghcr.io/trycua/linux:24.04
# or plain Ubuntu 24.04: apt-get install xfce4 xvfb dbus-x11 at-spi2-core python3-gi gir1.2-gtk-3.0 gir1.2-atspi-2.0,
# then start Xvfb :0 -screen 0 1920x1080x24 and an XFCE session with a private D-Bus and AT-SPI
```

You need Node 24 (we used 24.21) and Python 3.11 or later with PyGObject on the desktop, and the checkout of this
repository (or just `libs/cua-driver-bench`) as the desktop user. Then, inside the desktop, as root and then as the
desktop user:

```sh
sudo launch/xfce/provision-root.sh   # xdotool, wmctrl, LibreOffice 26.2.7, Google Chrome, GnuCash 5.17 (Flathub)
launch/xfce/provision-user.sh        # cua-driver 0.38.0, agent-desktop 1.2.0, npm ci of the four Electron apps
```

In a container neither Chrome, the Electron apps nor flatpak can create user namespaces, so the scripts run Chrome and
Electron with `--no-sandbox` through shims (Chrome then shows its unsupported-flag infobar) and run GnuCash outside
bubblewrap on its own GNOME runtime. On a full VM set `BENCH_NO_SANDBOX_SHIMS=0` for both scripts and skip
`shim-gnucash.sh`. LibreOffice shows its Welcome dialog and GnuCash its Tip of the Day on start, as on Windows.

**2. One trial.** Run it as the desktop user with the desktop's environment (`DISPLAY`, `DBUS_SESSION_BUS_ADDRESS`):

```sh
cd libs/cua-driver-bench/automated-eval/macos_bench
python3 launch/xfce_session.py --task IR-02 --run-index 0 --condition background \
    --out /tmp/trial --label cua-driver --timeout 360 -- launch/xfce/agent.sh cua-driver
```

`--condition` is `foreground` or `background`; `--run-index` 0 to 4 picks the fairness seed (the same seeds as the other
platforms). `agent.sh ARM` (`cua-driver` or `agent-desktop`) starts the agent: Claude Code 2.1.316 `claude -p` with
`--model claude-sonnet-5-5 --effort medium`, `MAX_THINKING_TOKENS=16000`, `--tools ""` (no tools beside the driver's MCP
server(s)), `--strict-mcp-config`, `--permission-mode bypassPermissions`, `--max-turns 45`, stream-json output, and the
task brief as the prompt with no system prompt. agent-desktop gets two servers, strict headless and `--headed`, and the
agent picks per call. The limit is 360 s and 45 turns per trial. `row.json` holds the checker result, the GUI-only
verdict and the sentinel's criteria; a trial counts as a background full pass only when the checker passed, there was
no GUI-only violation and all eight undisturbed criteria held (an unmeasured one counts as disturbed).

**3. The run.** The report's plan is, per arm, 8 background tasks (CDB-G02 to CDB-G04, MB-09, IR-01 to IR-04) and 10
foreground tasks, each with run indexes 0 to 4, one trial at a time per desktop (kill the task apps between trials; the
session resets the workspace itself). We ran six desktops in parallel, one per 8 vCPU / 32 GB cloud VM with the Linux
image as a 6 vCPU / 24 GB container, and ran the agent on a separate host with its MCP server over ssh; with the
agent on the desktop itself, as `agent.sh` does, the tool calls skip that network round trip. Pins: cua-driver
`cua-driver-rs-v0.38.0` linux-x86_64 release, agent-desktop 1.2.0 linux-x64 from npm. Not run on Linux: Browser Use (no
Linux desktop harness) and Codex computer use (not available on Linux).

### Linux on Hyprland (Wayland; the BenchLab tasks)

The Hyprland port runs the same GTK3 BenchLab (`linux/benchlab.py`) as a native Wayland client, with a
Wayland sentinel and GUI-only guard in [`automated-eval/macos_bench/hyprland`](automated-eval/macos_bench/hyprland).
It is built for Omarchy (Arch Linux with Hyprland 0.55 or later and a Lua config), for example Cua's
`ghcr.io/trycua/omarchy:edge` image. Seeds, the state file, the event log, the checkers and the sentinel
summary are the same as on macOS, Linux/X11 and Windows.

You need Python 3.11 or later with PyGObject, GTK 3 and AT-SPI, and `wl-clipboard`. Load
`hyprland/bench.lua` last from `~/.config/hypr/hyprland.lua` (it sets 1920x1080 so the shared window frames
fit), then run each trial as the desktop user with the session's environment (`WAYLAND_DISPLAY`,
`HYPRLAND_INSTANCE_SIGNATURE`, `XDG_RUNTIME_DIR`, `DBUS_SESSION_BUS_ADDRESS`). One trial:

```sh
python3 launch/hyprland_session.py --task IR-02 --run-index 0 --condition background --out ~/bench/IR-02-r0 -- <agent command>
```

Where Hyprland differs:

* **Placement.** A Wayland client cannot place its own windows, so the launcher floats BenchLab and the
  sentinel and gives them their frames through Hyprland's IPC socket. Window rules (applied on every trial)
  keep BenchLab's windows from taking focus when they open and open its dialogs over BenchLab's top-left
  corner, clear of the "User activity" window, as a sheet hangs from BenchLab on macOS.
* **Sentinel.** The compositor state comes from Hyprland's IPC: the active window, the stacking order of
  `clients` (a window counts as raised when it comes after the user window, draws over it and overlaps it;
  top and overlay layer-shell surfaces that overlap it count too, named after their owning process), the
  real pointer (`cursorpos`), the active and special workspaces and full-screen windows (Space), and a
  second window of the sentinel's own process (dialog). The clipboard is watched with `wl-paste --watch`
  (data-control), so a change counts whether or not the user window has focus. Key focus, typed keys,
  clicks and scrolls are GTK events on the user window, as on X11.
* **GUI-only guard.** A terminal emulator (Alacritty, Ghostty, kitty, foot, ...) started outside the
  runner's own processes, or a terminal or Omarchy TUI window active for three samples, fails and stops the
  trial. Shells alone are not counted (tool servers reached over SSH run under one). Tool inputs are also
  scanned for `hyprctl`, compositor `exec` dispatches, uwsm and Omarchy launchers, and terminal names.
* **Brief.** "on your Mac" reads "on this Linux computer".

`hyprland/oracle.py` solves each task through the GUI with real input (a uinput pointer and keyboard; the
desktop user needs access to `/dev/uinput` while it runs). It validates the port: the oracle passes every
checker, doing nothing fails every task and leaves the user undisturbed, and a deliberate focus change,
raise, pointer move, clipboard change, keystroke or workspace switch is each seen.
`tests/test_hyprland_tools.py` checks the guard, the brief, the descriptors and the window rules without a
desktop or a model.

### Windows

The Windows port of BenchLab and the sentinel is in
[`automated-eval/macos_bench/windows`](automated-eval/macos_bench/windows): Python with wxPython, so
every control is a native Win32 control that UI Automation exposes. Seeds, the state file, the event log
and the checkers are the same as on macOS and Linux (`probes/_common/benchlab_common.py`), and the
sentinel log is read by the same `swift/summarize_sentinel.py`.

You need Windows 11, Python 3.12 with `wxPython` (and `pywinauto` for the oracle only), and an
interactive desktop session: run the trials as a standard user signed in at the console, not from an
SSH or service session. One trial:

```powershell
python launch\windows_session.py --task IR-02 --run-index 0 --condition background --out C:\bench\IR-02-r0 -- <agent command>
```

`{brief}`, `{out}`, `{seed}` and `{mode}` in the agent command are filled in. The launcher starts
BenchLab and the sentinel (as `BenchLab.exe` and `BenchSentinel.exe`, copies of `pythonw.exe`), brings
the "User activity" window to the front in the background condition, arms the sentinel, runs the agent
with the GUI-only guard watching, then runs the checker and writes `row.json`. `windows\oracle.py` solves
each task through the GUI with real input; `tests/test_windows_desktop.py` checks that the oracle passes
every task, that doing nothing fails and leaves the user undisturbed, and that a deliberate disturbance
is seen.

#### The comparison setups on Windows

Each setup is one stdio MCP server in an `--mcp-config` file, run in the same interactive desktop session as the
trial. The adapters and the filter are in `automated-eval/macos_bench/tools/`; paths below are examples.

| Setup | Install | MCP server command |
| --- | --- | --- |
| agent-desktop 1.2.0 | `npm install agent-desktop@1.2.0` (prebuilt `win32-x64` binary included) | `python -I -B tools\agent_desktop\ad_mcp.py` with `AD_BIN=<...>\node_modules\agent-desktop\bin\agent-desktop-win32-x64.exe` (agent-desktop 1.2.0 also has its own `mcp` subcommand; the Windows release run used that one) |
| Browser Use Windows harness 0.2.2 | `pip install "git+https://github.com/browser-use/windows-harness@46a37cf1d411c7816adffc274d5bdc2cca2bd9f0"` | `python -I -B tools\browser_use_harness\wh_mcp.py` with `WH_BIN=<...>\Scripts\windows-harness.exe` |
| Codex Computer-Use (ChatGPT/Codex app 26.1029.9216.0) | Install the app, enable Computer Use, sign in with your own ChatGPT account with Work or Codex access | `python tools\codex_cu\codex_cu_filter.py --allow BenchLab --windows-app "<app dir>\resources"` |

For Codex on Windows the filter does four things the plugin expects of the ChatGPT app and Claude Code does not
do: it adds the sandbox metadata to tool calls, answers the per-app approval prompt (accepting only apps on
`--allow`, here BenchLab, and declining everything else), answers Claude Code's `server/discover` probe locally,
and flattens the `js` tool's top-level `oneOf` input schema, which the Anthropic API rejects. Computer Use runs
foreground only on Windows, so run the foreground condition for it; the Windows release tables mark it that way.

A config file looks like this (server names are the ones the runner and the analysis expect: `agentdesktop`,
`browseruse`, `codex-cu`):

```json
{"mcpServers": {"agentdesktop": {"command": "python", "args": ["-I", "-B", "tools\\agent_desktop\\ad_mcp.py"],
  "env": {"AD_BIN": "C:\\bench\\agent-desktop\\node_modules\\agent-desktop\\bin\\agent-desktop-win32-x64.exe"}}}}
```

The agent command that `launch\windows_session.py` runs is then the same `claude -p` call as on macOS (see
[`RUNNER.md`](automated-eval/macos_bench/RUNNER.md), "The claude invocation"), with `--strict-mcp-config
--mcp-config <file>`, `--allowedTools mcp__<server>` and a system prompt that says "Windows desktop".

Where Windows differs:

* **GUI-only guard.** A shell or script host (PowerShell, cmd, Windows Terminal, the script hosts,
  mshta, WSL) started in the desktop session outside the runner's own processes, or a side-door window
  in front, fails and stops the trial. Tool inputs are also scanned for PowerShell, cmd and script-host
  commands. A shell whose parent is the setup's own binary (`--tool-exe cua-driver.exe`, for example: Cua
  Driver starts PowerShell to read browser processes) is part of the tool, as a driver's helper process is
  on macOS: it is logged in `gui_only.tool_helpers` and does not count. A shell started from code the agent
  supplied (a harness's Python `exec`, a JavaScript REPL) has an interpreter as its parent and still counts.
* **Sentinel.** Windows has no signals, so the runner arms it through a control file. A window counts as
  raised when it is above the user window in the z-order and overlaps it. The desktop measure is
  `IVirtualDesktopManager`; a dialog on the user's app is a window owned by the user window.
* **Dialogs.** BenchLab's dialogs are owned by its window and disable it while open. When BenchLab is not
  in front, a dialog opens without activation just above BenchLab, so BenchLab never raises itself.
* **MB-09.** Rows reorder by a native list drag (the list view's begin-drag, then the button release
  over a row).
* **MB-10 and MB-11.** Hover and tooltips follow the real pointer on Windows too (mouse-leave tracking
  and the tooltip control read the cursor position), so both stay foreground-only. A tooltip counts as
  shown when BenchLab's own tooltip window is visible.
* **Brief.** "on your Mac" reads "on this Windows PC".

#### Multi-app tasks on Windows (CDB-G02 to CDB-G04)

The same launcher runs the pack's multi-app tasks from each task's own
`platform/launch.windows.json` (`windows/cdb.py`): it resets the workspace with the pack's setup and
byte-level verify, starts the apps, gives each window the descriptor's bounds, runs the agent as above, then
runs the pack's evaluator and leaves the final workspace in `DIR\workspace-final.zip`. The workspace is
`%USERPROFILE%\cdb-s0N`; `{workspace}` in the agent command is filled in.

```powershell
python launch\windows_session.py --task CDB-G03 --run-index 0 --condition background --out C:\bench\CDB-G03-bg-r0 -- <agent command>
```

Install before the trials (the network can be off during them):

| Component | Version used | Where the descriptor expects it |
|---|---|---|
| Node.js | 22 or later (24.15.0 used) | `node` on `PATH` (the CDB-G04 archive site and its evaluator) |
| Electron | 43.8.1, from each app's `package-lock.json` | `npm ci` in `taskpack/tasks/shared/cdb-s0N/apps/<app>`; if npm skips Electron's install script, run `node install.js` in `node_modules\electron` |
| LibreOffice | 26.2 (26.2.6.3 used) | `C:\Program Files\LibreOffice\program` |
| GnuCash | 5.17 (`gnucash-5.17.setup.exe`, sha256 `a3e8049755e536f647640762a483ebe1b6c79cc50cc81a746fa64a404e98d271`) | `C:\Program Files (x86)\gnucash\bin\gnucash.exe` |
| Google Chrome | stable (157.0.8103.39 used) | `C:\Program Files\Google\Chrome\Application\chrome.exe` |

Where the multi-app tasks differ on Windows:

* **Electron apps.** Each app runs from a copy of the pack's own `electron.exe` named after its window title
  (`Copperfield Mail.exe`, `Rillwatch Cases.exe`, ...) in the same `dist` folder, as macOS gives each app its
  own bundle (Amendment 4): same binary, code and arguments, but a setup that names apps by process can tell
  them apart.
* **GnuCash preferences.** GnuCash keeps its preferences in the registry on Windows
  (`HKCU\Software\GSettings\org\gnucash`), outside the task workspace, so the reset deletes that key:
  every trial starts GnuCash with default preferences.
* **LibreOffice updates.** LibreOffice's Windows updater can replace the installation when Calc starts. Turn
  it off for the bench user before the trials: `org.openoffice.Office.Update/Update/Enabled` and
  `org.openoffice.Office.Jobs/Jobs/UpdateCheck/Arguments/AutoCheckEnabled` set to `false` (as
  `Software\Policies\LibreOffice` registry policies, which an administrator writes).
* **Codex approvals.** Codex computer use names a Windows app by its process when it asks for approval:
  `soffice.bin` for LibreOffice, `GnuCash`, `Google Chrome`, and the Electron apps by their named executables
  (`copperfield mail`, ...). Put those names on the adapter's `--allow` list for CDB-G02 to CDB-G04; a name
  missing from it is declined and the setup cannot use that app.
* **Leftovers.** Before and after a trial the launcher stops the task's own executables in the desktop
  session by exact name and whatever listens on the task's loopback port (4184 for CDB-G04).
* **Validation.** `windows\cdb_oracle.py` stands in for the agent: by default it applies the scripted
  correct solution of the pack's own test module to the workspace (the checker passes), `--noop` does
  nothing (the checker fails, the user window stays undisturbed) and `--disturb` steals focus once (the
  sentinel sees it). `tests/test_windows_cdb.py` checks the descriptors, the named executables and the
  oracle without a desktop.

## Adding tasks

New tasks follow the same layout: a BenchLab task gets `probes/<ID>/` (with
`task.json`, `brief.md`, `render_brief.py`, `evaluate.py` and `PROVENANCE.md`)
and, if needed, a BenchLab mode; a multi-app task goes into `taskpack/tasks/`
with a selector in `probes/<ID>/task.json`, its tree digest in `pins.json`, and a
`PROVENANCE.md`. A task joins the Bench v2 list (`bench_v2.V2_TASKS`) only
through a dated amendment committed before its first trial. See
[`taskpack/README.md`](taskpack/README.md).
