---
title: How Lume creates local macOS sandboxes
description: How Lume turns Apple restore images into unattended local macOS sandboxes.
---

Lume creates vanilla macOS VMs from Apple restore images. The unattended setup
prepares the installed guest on disk, so the workflow does not depend on GUI
clicks or a particular Setup Assistant layout.

## The setup sequence

When you run `lume create` with `--unattended goldengate`, `--unattended tahoe`
or `--unattended sequoia`, Lume:

1. Installs macOS from the IPSW into a new VM disk.
2. Boots the VM once so macOS materializes its first-boot state.
3. Stops the VM and mounts its Data volume on the host.
4. Reads the guest's `SystemVersion.plist` off its System volume.
5. Patches the guest account and login configuration offline, and records
   that release as the account's last login.
6. Enables SSH, autologin, and the no-sleep settings.
7. Boots the VM again and verifies SSH before finalizing creation.

The default account is `lume` with the initial password `lume`. Change that
password before using the VM for sensitive work.

## Why the setup is offline

GUI automation depends on display timing, window state, and the controls that a
particular macOS release exposes. Disk setup writes the desired guest state
directly and keeps the verification step small: Lume checks that the guest
boots and accepts SSH.

## Boot policy changes use Recovery

Offline setup can change guest files, but it cannot sign Apple silicon boot
policy. SIP changes therefore use the VM's paired Recovery environment and a
normal boot verification. Read [How SIP works in Lume
VMs](/concepts/how-sip-works-in-lume-vms) for the policy model.

## Presets and images

The `goldengate`, `tahoe` and `sequoia` presets use the same offline patcher;
they differ only in their health-check budget. The patcher is not pinned to a
release: it reads the installed guest's build from its System volume and stamps
that into Setup Assistant's state.

The patcher also records that release as the last one the `lume` user logged in
to, in `~/Library/Preferences/loginwindow.plist`. Without that record,
loginwindow treats the account's first graphical login as a brand-new user.
UserAccountUpdater then schedules "MiniBuddy" (`Setup Assistant -MiniBuddyYes`)
with its "new user account" reason, which always runs the Apple Account
sign-in, whatever else is marked as seen. A guest can have `.AppleSetupDone`, a
working autologin and a passing SSH health check and still land there, because
the SSH check never looks at the screen.

Because that first login is then an ordinary same-version login, macOS skips its
new-user initialization. On macOS 27 the visible effects are three Dock
placeholders for Keynote, Numbers and Pages, which are not installed, and a
menu-bar clock without the date.

The IPSW flow creates a fresh vanilla guest each time. Registry snapshots remain
available for workflows that need a previously prepared disk, but they are not
required for unattended setup.
