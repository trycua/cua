`relay.cua.ai` (and any self-hosted `cua-relay`) does two jobs:

- **For Cua machines, it coordinates a WireGuard®-based mesh.**
  It introduces the two ends. When they can't reach each other directly, it
  forwards their traffic as ciphertext it can't read. This is the default
  for current versions of the Cua app, CLI and SDK.
- **For everything else, it is a trusted, TLS-terminating proxy, not a blind
  relay.** This covers the browser viewer, web agents, share links and older
  Cua versions.

This page says plainly what each of those means, and we keep it current as the
relay changes. If anything here reads as a surprise, that is a bug in this
page: tell us.

## Which path you are on

| Your Cua version | Connections to your machines |
|---|---|
| `cua` CLI and SDK 0.7.0 or later, Cua Spaces app 0.13.0 or later, `cua-spacesd` 0.7.0 or later | **The mesh by default** (`CUA_MESH=prefer`): end to end. They use the HTTPS path only when the mesh isn't available (see [Turn it off, or require it](#turn-it-off-or-require-it)). |
| Older versions (`cua` 0.6.x and earlier, Cua Spaces app 0.12.x and earlier) | **The relay's HTTPS path**, unless the mesh beta was turned on. They keep working, but the relay can read their sessions in transit. Update to get the mesh. |

A connection uses the mesh only when **both ends** support it: the machine you
connect from and the machine you host. A mixed account (a new laptop and an
old machine, say) uses the HTTPS path for that pair. Update in this order:
the Cua Spaces app first, then the `cua` CLI and SDK, then each hosted
machine (`cua host setup` again, or let the app update it).

## The short version

- **Over the mesh (Cua apps, CLI, SDK and daemon, on current versions):**
  traffic between your machine is encrypted end to end with
  WireGuard between keys that never leave the two ends. Most connections go
  directly between the two networks; when they cannot, the relay forwards
  the encrypted packets. **The relay cannot read or change shell output,
  files, input, the desktop stream, Keyvault passwords or teleport
  bundles.** It sees who talks to whom, when, and how much. See
  [End-to-end encrypted connections](#end-to-end-encrypted-connections).
- **Over the relay's HTTPS path (the browser viewer, web agents, older Cua
  versions, `CUA_MESH=off`, or a self-hosted relay without `--mesh on`):** TLS ends at the relay's ingress, and the
  relay parses every request it forwards (gRPC, gRPC-Web, WebSocket
  upgrades, `/files` transfers) to route and authorize it. **It can read the
  plaintext of anything it proxies while the request is in flight**:
  shell output, file contents, the desktop media stream, keystrokes and
  clipboard data sent as input, and, unless sealed (below), Keyvault
  passwords and teleport session bundles.
- **Runs on all your machines** (`cua sb run --on auto`, durable Spaces):
  the relay stores the job log and passes requests between your machines,
  but everything a job is and produces is **sealed on your machines** with
  keys only your added machines hold. The relay sees job ids, the kind of
  each change, which machine an attempt went to, and sizes; never a command,
  environment, input, output or result. See
  [Runs on all your machines](#runs-on-all-your-machines).
- It does not **store** traffic, env tokens or account tokens on either
  path. On the HTTPS path it strips a client's credentials and forwards a
  short-lived signed assertion instead (account mode), or forwards a
  self-hosted relay's env token unmodified without persisting it (static
  mode). On the mesh, account tokens go only to the relay, never to the
  machine, and a static relay never sees the env token at all (a machine
  proves it holds the token to the machine itself). See the relay README
  (`libs/cua-spacesd/crates/cua-relay/README.md` in the cua repository) for
  the exact claims and how they are enforced in code.
- **The relay is still a trusted coordinator.** In account mode, the relay
  tells each machine which peers are yours (your machines, and
  the accounts a machine is shared with) and what each peer's mesh public
  key is. Both ends trust that list, just as they trust the relay's signed
  assertions on the HTTPS path. So a compromised relay could add a machine of
  its own as a peer, or hand your machine a key of its own in place of a
  machine's key, and then sit in the middle of the connections that follow.
  It can't decrypt traffic sent under keys it doesn't hold. A
  static-token relay can do less: each machine accepts only the machines that
  proved they hold its env token, and ignores any other peer the relay names.
  We are working on machine-signed keys, so that only your added machines can
  vouch for a peer's key. Until then, if you need a coordinator you don't
  have to trust, run your own relay or [use your own
  tailnet](/spaces/guides/your-tailnet).
- **The HTTPS path is quiet by default.** With the default `CUA_MESH=prefer`,
  a connection that can't use the mesh falls back to the HTTPS path, and only
  a log line says so. Set `CUA_MESH=require` on your machines,
  and their connections never fall back to a path the relay can read.
- A compromised relay process, relay host, or a memory dump of either, is
  equivalent to a compromised session for every machine currently routed
  through it on the **HTTPS path**: it can mint assertions the machines still
  trust, and read whatever crosses it meanwhile.

## The mesh (on by default)

[End-to-end encrypted connections](#end-to-end-encrypted-connections) are
on by default. When both ends and the relay support them, a `relay:` Space no longer goes through
the HTTPS path, and the relay forwards only ciphertext it cannot read or change.
Everything in the next sections describes the HTTPS path, which stays in use for
everything else: the browser viewer, web-hosted agents, machines
without the mesh, and anything where the mesh is not available (or you set
`CUA_MESH=off`).

## What the relay can still read

These always use the relay's HTTPS path, so the relay can read them in
transit, whichever Cua version you run:

- **The browser viewer**, and anything else that opens a machine through
  `https://<relay>/m/<computer>/…`: web or Cloudflare-hosted agents, and MCP
  clients that connect to a machine through a relay URL.
- **Share links** (`cua share`): a private, team or public link is served
  through the relay to whoever opens it.
- **A Keyvault site-login password** sent to a `relay:` Space over the HTTPS
  path. This is refused by default, and needs your acknowledgement for each
  sign-in (see [Sealed delivery](#sealed-delivery-where-it-stands)).

And for Cua's own apps, CLI and SDK, these use the HTTPS path:

- machines on [older versions](#which-path-you-are-on);
- anything set to `CUA_MESH=off`;
- a connection that fell back from the mesh under the default `prefer`;
- a self-hosted relay started without `--mesh on`.

## What crosses the relay

| | Over the mesh | Over the HTTPS path |
|---|---|---|
| gRPC (shell, files, input) | Ciphertext only (direct when possible) | Parsed and forwarded: **readable** |
| Desktop media stream | Ciphertext only; QUIC over the mesh, direct or relayed | Parsed and forwarded (TCP over the relay): **readable** |
| `/files` transfers | Ciphertext only | Parsed and forwarded: **readable** |
| Account tokens | Sent to the relay only, to join the mesh; never to the machine | Stripped and replaced with a signed assertion |
| Env tokens (static relays) | Never sent to the relay (a proof to the machine instead); travel to the machine inside WireGuard | Forwarded unmodified, not stored: **readable in transit** |
| Keyvault site-login password | Inside WireGuard to the machine | **Gated**: refused over a `relay:` Space by default; sending anyway needs your explicit, per-sign-in acknowledgement (see below) |
| Teleport session bundle (cookies, Safe Storage keys) | Inside WireGuard to the machine | **Sealed** once the Space's guest key is pinned; **gated** otherwise |
| Who connects to which machine, when, how much | Visible (it coordinates and may relay) | Visible |
| Batch runs' job log and requests (`--on auto`) | Stored sealed: commands, environments, outputs and results are ciphertext; job ids, placements and sizes are visible | Same (sealed before it leaves the machine) |

Which path a connection took shows in the logs of the machine (`relay
Space over the mesh`, or `using the relay's HTTPS path` with the reason).
With `CUA_MESH=require`, a machine never falls back to the HTTPS path.

## Runs on all your machines

A batch run on your machines (`cua sb run --on auto`, `on="auto"` in the SDK
and MCP tools) and a durable Space are coordinated by one of your machines,
and the relay keeps their job log so that another machine can take over.
That log, its snapshots, and the requests and answers between your machines
are encrypted end to end:

- **Your machines hold the keys.** Each signed-in machine has a pool key
  (X25519, in the same store as its machine key: the OS keychain for
  Cua-signed builds). It signs the pool key with its own machine key and
  registers it with the relay. The account's data key is wrapped to each
  machine's pool key with HPKE (RFC 9180) in authenticated mode, so a machine
  only accepts keys another of your machines wrapped. The relay stores the
  wraps and cannot open them.
- **Everything about a job is sealed** before it leaves the machine, with
  XChaCha20-Poly1305: its command, environment, input, image and resources,
  its output and result, durable Spaces' addresses and tokens, your machines'
  details, and every request and answer between your machines. Each sealed
  entry is bound to its position and readable fields, so the relay cannot
  move it, swap it or change it unnoticed.
- **New and revoked machines.** A machine you add is given the keys by any of
  your machines that has them, within seconds, and can then take over runs.
  At least one of those machines must be online for that: until then, a run
  on your machines from the new machine fails within seconds and names the
  machines that hold the keys and when the relay last saw them (`cua
  machines` shows them too). Open Cua on one of them, or revoke the ones
  you no longer have. A new machine never makes new keys on its own while a
  machine that holds them is still in your account, however long ago it was seen:
  only you can tell an asleep laptop from a lost one, and the relay can't
  make your machines drop the keys by hiding the others. Runs on the machine
  itself (`--on local`, the default for `cua run`) never need the keys.
  When you revoke a machine, the relay refuses anything sealed under the
  keys it had until one of your machines makes new ones without it, which
  happens on the next write: nothing written after it left is readable by
  it, even with the relay's help. What it could read before stays readable to
  it. If every machine that held the keys is revoked, the next machine starts
  new keys and the log nobody can read is dropped (its runs are lost).

| The relay can see | The relay cannot see |
|---|---|
| Job ids, run ids, and how many jobs a run has | Commands, arguments, environment variables, input |
| The kind of each change (submitted, dispatched, running, ended) and which entry ends a job | Outputs, exit codes, errors and results |
| Which of your machines an attempt went to, and the attempt's number | Images, resources and timeouts |
| Which machine coordinates, its epoch, and when | Durable Spaces' names, addresses and tokens |
| Sizes and timing of every entry and request | Your machines' details as the coordinator records them |
| Which machines hold the keys, and the key generation | The keys |

The relay checks what it can without the keys: it stores only sealed data
(anything else is refused), only under the newest key generation, keyrings
wrapped by and to your account's added machines, and the fencing that
keeps one coordinator and one result per job. How this was checked (a model
checker, a simulation of the real code, and fault injection on real
machines) is in the
[design](https://github.com/trycua/cua/blob/main/docs/rfcs/pool-self-coordination.md).

<Callout type="warn">
  The relay still decides which machines are your account's. A relay that is
  actively malicious could add a machine of its own (as it could add a
  peer to the mesh, above) and be given the keys for what is written after
  that; it could not read anything sealed before, and the machine shows in
  `cua devices ls` and in the app as one the keys are
  shared with. Run your own relay if that is not acceptable. Jobs reach your
  machines over the mesh (ciphertext); with the mesh off they use the HTTPS
  path, where the relay can read them in transit (above).
</Callout>

## Sealed delivery: where it stands

We seal teleport secrets end to end to the destination machine's own key, so
the relay forwards only ciphertext for a sealed delivery. The construction:
an ephemeral X25519 key per delivery, HKDF-SHA256, XChaCha20Poly1305, bound
to the Space id, a purpose string and a timestamp, with replay rejection
(`cua-machine-seal`; no hand-rolled crypto, every primitive is a vetted
RustCrypto / dalek crate). A guest's spacesd generates its own keypair on
first start (0600 on disk) and reports the public half through its
capabilities; the host pins it on first use (trust-on-first-use) and seals
every subsequent teleport delivery to it.

<Callout type="warn">
  **Current state, honestly:** teleport's sealing and the gate are both live.
  A Space whose image was built before this shipped reports no guest key, so
  the teleport `ImportSession` path (which the Keyvault broker's combined
  prompt also uses for cookies and session data) refuses to send over a
  `relay:` Space from such an image unless you explicitly acknowledge the
  risk for that one delivery. Republishing the guest image is what makes
  the refusal go away, by making the delivery sealed instead. The
  **Keyvault site-login password path** (typed directly into a page via
  `browser_type`) is **gated the same way, but not yet sealed**: a saved
  password still crosses the relay as a plain request argument when you
  acknowledge the risk, since there is no practical way yet to seal a single
  driver-call argument the way a whole bundle upload is sealed. Treat an
  acknowledged site-login sign-in into a `relay:` Space the same as you
  would treat typing that password into any other network request that
  crosses a proxy you do not control, until this page says otherwise.
</Callout>

**Local and direct Spaces, and connections over the mesh, are unaffected
either way**: the relay cannot read them, so there is nothing to seal
against. The gate and sealing apply to the HTTPS path only.

## Other hardening already shipped

- **A second factor for new machines.** Re-signing in adds only
  your own machine (a re-key, or your account's first machine). A brand-new
  machine on an account that already has an added machine needs an approval
  from an added machine, or a sign-in whose token itself proves a second
  factor. A verified email alone is not enough.
- **New machines are flagged.** A machine registered without an added
  machine's signature or MFA is marked unconfirmed until an added machine
  vouches for it.
- **A separate origin for machine content.** Machines no longer render as
  HTML, register a Service Worker, or set cookies on the relay's own
  origin outside the one known viewer path; a fully separate registrable
  domain for machine content is designed and partly implemented in code,
  pending a DNS/TLS rollout.
- **Bounded relay memory.** A per-machine cap on buffered bytes and streams,
  plus a relay-wide budget with backpressure, so one machine (or one
  account's worth of them) with slow-reading clients cannot take down every
  other machine's connection.
- **A tamper-evident, exportable audit log**, hash-chained like the
  Keyvault's own, with `GET /v1/audit?format=jsonl` for export to your own
  SIEM or backup.
- **The migration grace period (a stolen session alone reaching every
  machine) is off by default**, and time-boxed to an announced rollout
  window when it does run.
- **State writes that fail loudly.** The relay appends audit events and
  sessions to their own logs instead of rewriting its state per event, cleans
  up after an interrupted write at startup, refuses a machine
  change it could not store (rather than acknowledging it), and keeps a
  reserve of free space that pool data cannot use, so sign-ins and machine
  changes keep working when pools fill the volume. A self-hosted relay
  reports this on `GET /readyz` (a real write probe, free space, each
  store's last write) and `GET /metrics`; alert when `/readyz` fails, free
  space drops under 20%, or any write fails. The relay's
  [README](https://github.com/trycua/cua/tree/main/libs/cua-spacesd/crates/cua-relay#state-and-monitoring)
  lists the rules.
- **No Nagle delay on relayed calls.** The relay and machines disable
  Nagle's algorithm on the tunnel, which used to add about 80 ms to each
  small relayed call.

## End-to-end encrypted connections

<Callout type="info">
  **On by default** in the Cua Spaces app (every channel), the `cua` CLI and
  hosted machines, once they are on a version that includes it. Where the mesh
  cannot be used (a self-hosted relay without one, an older machine, a
  network that blocks it) Cua uses the relay's HTTPS path, as before. To turn
  it off, set `CUA_MESH=off` (below).
</Callout>

With the mesh on, a machine that opens a Space on one of your machines
(`relay:<machine>`) connects to it over a WireGuard®-based mesh that runs
inside Cua itself, instead of through the relay's HTTPS path. The relay
coordinates the mesh but never holds a session key: shell, files, input,
screen and Keyvault deliveries cross it only as ciphertext.

- **End to end.** Each machine makes its own key pair on first
  use; the private half never leaves it. Traffic between two of them is
  encrypted with WireGuard between those two keys.
- **Direct when possible.** Two ends on the same network connect directly.
  Otherwise packets go through the relay, still encrypted between the two
  ends: the relay forwards them without being able to read or change them.
- **Inside Cua only.** There is no network interface, no VPN profile, no
  system extension and nothing that needs administrator rights. Mesh
  addresses (`fd5c:a000::/32`) exist only inside Cua, so the mesh never
  conflicts with Tailscale or another VPN you already run, and it carries
  Spaces traffic only.

### Turn it off, or require it

Both ends use the mesh when it is available: the machine you connect from and
the machine you host. Each end decides for itself with `CUA_MESH`.

| `CUA_MESH` | Behavior |
|---|---|
| unset or `prefer` (default) | The mesh when both ends and the relay support it; the relay's HTTPS path otherwise, with a log line saying why. |
| `off` | The relay's HTTPS path only, as before the mesh. |
| `require` | The mesh or nothing: a relay that could read the session is never used. |

- **On the machine:** set `CUA_MESH` where `cua` runs (your shell, or the
  environment of the cua daemon; restart the daemon with `cua daemon stop`
  after changing it).
- **On a hosted machine:** to turn it off there, run `cua host setup` with
  `CUA_MESH=off` set. The setting is kept for the host's service until you run
  setup again without it.

`cua spaces ls` lists the same machines either way. With `prefer`, a machine
or relay that does not speak the mesh is used over HTTPS, so mixing
updated and older machines works.

### Who can connect

The relay applies the rules you already manage:

- A machine added to your account reaches the machines your account owns
  and those shared with it, while their sharing is on.
- The machine sees each machine with the same identity as before (account,
  verified email, owner, editor or viewer), and its own host policy still
  decides what that caller may do.
- Stopping sharing, removing someone from a share list, or revoking a machine
  takes it off the mesh within seconds and cuts its open connections. The
  next call says why.

### Your plan allowance

A desktop view, terminal or agent session over the mesh counts toward your
plan's live sessions, the same as one over the relay's HTTPS path, and one
machine reached both ways at once counts once. Remote hours count only the
time a session's traffic goes through the relay: a direct connection uses
none. `cua usage` and the app's Settings show both.

### When the network changes

Connections belong to the two ends, not to a network path. When a laptop
moves from Wi-Fi to Ethernet or its public address changes, traffic moves to
the relay for a moment and back to a direct path as soon as one answers. A
relay restart does not interrupt direct connections; a connection that was
going through the relay resumes when the relay is back.

### Self-hosted relays

A self-hosted `cua-relay` coordinates a mesh when you turn it on with
`--mesh on` (or `CUA_RELAY_MESH=on`); without it, machines use the HTTPS
path. Give it a UDP port for STUN so machines learn their public addresses:

```bash skip="no-runner"
cua-relay --tokens "$TOKEN" --public-url https://relay.example.com \
  --mesh on --mesh-stun-listen 0.0.0.0:3478
```

The relay advertises `relay.example.com:3478` (override with
`--mesh-stun`). Open UDP 3478 to it. `--mesh off` (the default) leaves the
mesh off (machines then use the HTTPS path); `--mesh-relay off` keeps the
coordinator but stops relaying packets (machines that cannot reach each other
directly then cannot connect over the mesh). The mesh registry persists next
to the state file (`<state>.mesh.json`), so a restart keeps every machine's
keys.

On a self-hosted relay with static tokens, a machine reaches a machine only
after proving it holds that machine's env token. The machine checks the
proof itself and remembers the machines it accepted; the relay only passes the
proof along and never sees the token.

### Use your own tailnet instead

Teams that already run Tailscale or Headscale can host Spaces on their own
tailnet instead, with the tailnet's identities, ACLs and SSO deciding who
connects: see [Use your tailnet](/spaces/guides/your-tailnet).

### What still goes through the relay's HTTPS path

See [What the relay can still read](#what-the-relay-can-still-read).

### Firewalls

Direct paths use UDP. Each end picks a UDP port on its own; outbound UDP is
all it needs. On networks that block UDP, the mesh still works through the
relay, over HTTPS to the same relay address as the rest of Cua.

## What the relay stores, and for how long

This is what `relay.cua.ai` keeps. A self-hosted relay keeps the same things
on its own disk.

| Data | Why | How long |
|---|---|---|
| Your account id, email and name; your machines' names, owners and share lists | Routing, and checking who may connect | Until you remove the machine or delete your account |
| Your added machines: their public keys and sessions | Adding a machine to your account | An addition ends 30 days after it was last used; removed when you revoke the machine |
| Mesh registry: each machine's and machine's WireGuard public key, and the network addresses it reports (up to 32 public and local IP addresses per node) | Introducing the two ends of a connection | While the machine is registered |
| Which accounts reached each machine recently, and whose access was revoked (grants) | Making a revoke also cut the short-lived tickets a machine issued | About a day: each entry is dropped after 24 hours |
| Your account's audit log (hash-chained) | Your own audit trail, exportable with `GET /v1/audit?format=jsonl` | The latest 5,000 entries per account |
| Pool keys (wrapped to your machines) and the sealed job log | [Runs on all your machines](#runs-on-all-your-machines) | Kept with your account; the relay can't open them |
| Usage totals (hosted relay) | Your plan's allowance | Totals for the current calendar month |
| Usage analytics events (PostHog, EU) | Product metrics on relay usage | Sent under a pseudonymous id derived from your account id, with no person profile; PostHog's retention applies |
| Server logs | Operating the service | 30 days. Your account id can appear in them; emails are redacted |
| Backups of everything above (hosted relay) | Restoring the relay if its disk is lost | Encrypted snapshots, taken hourly and kept 3 days |

The relay never stores session traffic, file contents, screen images,
keystrokes or Keyvault secrets, on either path.

**Delete your account** (in the account app) and the relay erases everything
in the table that belongs to you, including your entries in other people's
share lists and any analytics events it has not sent yet. Logs age out within
30 days, backups within 3 days, and analytics events already sent stay under
the pseudonymous id.
